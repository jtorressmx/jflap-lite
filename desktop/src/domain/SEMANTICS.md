# Turing migration evidence

The domain implementation was reconstructed from the selected Java source tree. The observations below are grounded in the listed sources and supplemented by the headless Java differential verification described under Validation.

## Preserved behavior

- `automata/SimulatorFactory.java` chooses `NDTMSimulator` for the entire machine when `TMNondeterminismDetector` finds at least one nondeterministic state. `nondeterministicStates` and `readsOverlap` port that detector's actual string comparisons, including its unusual treatment of assignments and negation.
- `automata/turing/TMSimulator.java` uses a single successor, puts `!` transitions after other transitions, recognizes `~` as any symbol, recognizes `!x` as anything except x, and recognizes comma-delimited `a,b}v` assignment. Assignment values persist until resetting a simulation. Writing `~` preserves the current cell; writing a known one-character variable substitutes its value.
- `automata/turing/NDTMSimulator.java` compares read labels literally and writes labels literally. Consequently a machine selected as nondeterministic does **not** apply deterministic wildcard/negation/assignment behavior. It also never produces a halted configuration. These observable legacy differences are preserved.
- `gui/action/NoInteractionSimulateAction.java`, `gui/sim/ConfigurationButton.java`, `gui/action/MultipleSimulateAction.java`, and `gui/sim/multiple/InputTableModel.java` inspect `Configuration.isAccept()`. Electron acceptance therefore follows `TMConfiguration`'s enabled final-state and halt filters in both modes. The unused-for-these-UI-actions `NDTMSimulator.isAccepted()` method ignores the preference; it is not the selected UI behavior.
- `automata/turing/Tape.java` permits unbounded motion in both directions. The renderer uses stable signed coordinates instead of shifting all indices on left extension, preserving relative head/cell behavior. Tape cells use UTF-16 code units like Java `char`.
- `Tape.getOutput()` returns the substring beginning **at the head**, stopping before the first blank. It is distinct from the entire nonblank tape contents.
- `gui/environment/Profile.java` defaults: accept by final state enabled; accept by halt, stay, and transitions from final states disabled. `gui/action/SimulateAction.java` blocks all simulations if any final state has outgoing transitions while the preference is disabled. At the user's request, Electron enables transitions from final states by default, including when restoring old settings. `createSession` still supports the explicit legacy restriction for API callers and differential tests. Reaching a final state still accepts when final-state acceptance is enabled; outgoing transitions do not invalidate that state.
- `TMTransition.java` maps an empty symbol to `□` and bare `!` to `!□`. Writes have exactly one UTF-16 unit. Constructor accepts L/R/S; the editor's stay preference restricts newly edited transitions, while imported S transitions remain valid.
- The normal Java launch disables assertions. Consequently `ab}v` is accepted by the constructor and matches the first character `a` of its assignment token; `!ab` likewise compares only against `a`. Assignment variable names can contain several characters, although write labels still have one character. The port preserves these actual rules. Empty internal assignment tokens raise a clear renderer error instead of Java's `charAt(0)` exception; trailing empty tokens are removed like Java `String.split`.
- The deterministic terminal timeline matches Swing: one step produces a halted configuration, and the following step marks it rejected unless halting acceptance is enabled. The halted clone retains the original parent so the trace does not gain a spurious transition. Rejected nondeterministic branches appear for one step. On the next step, `ConfigurationPane.getValidConfigurations` selects NORMAL cards and `clearThawed` clears every previous non-frozen card, including accepted/rejected cards. `stepInteractiveSession` permits continuing after an accepted or rejected frontier, clears those terminal branches, retains frozen branches, and advances only normal branches; `runMachine` stops on the first accepting frontier.
- `file/xml/TMTransducer.java`, `AutomatonTransducer.java`, and `TransducerFactory.java` define standard one-tape `.jff`. States, names, labels, initial/final markers, coordinates, notes, and explicit transition control points roundtrip. Empty read/write tags represent blanks. Missing move defaults to R. State references, duplicate state identifiers, multi-tape input, and block machines are validated. Equal duplicate transitions are ignored like `Automaton.addTransition`.

## Deliberate desktop adaptations and remaining numerical differences

- At the user's request, the read/write editor accepts one UTF-16 character. Imported expressions retain their original data and execution semantics. Transition labels display arrows; the movement selector uses Spanish direction names without an arrow prefix. `.jff` files retain L/R/S. Numeric tape coordinates remain internal; acceptance and rejection color the tape green and red respectively. Tape motion is presentation only: the engine still advances an exact discrete cell per transition.

- The execution APIs return a distinct `limit` result after a configurable bound (default 1,000 steps or 2,000 simultaneous configurations), rather than freezing the page or prompting through Java Swing's periodically doubled continuation warning.
- Missing XML positions receive a usable grid position rather than Java's three GEM passes. Imported positions are retained.
- Malformed/non-numeric/negative XML IDs are rejected clearly. Java `AutomatonTransducer.parseID` unexpectedly maps malformed input to -1 despite documentation describing rejection; that malformed-input defect is not reproduced.
- XML DTD and entity declarations are rejected. Standard JFLAP exports do not require them.
- Legacy `<block>` states with a unique, explicitly empty referenced `<MachineN/>` definition are imported as ordinary states. The supplied `contadorOs.jff` exercises this format with 21 states and 77 transitions. Missing/ambiguous references and executable submachine contents are rejected rather than silently discarded. Saving emits standard states; Java differential tests verify that normalized machine's complete execution traces, not nested-block execution.
- The optional root `name` attribute preserves the document title. Java ignores that extension. Generated state identifiers are normalized to numeric JFLAP identifiers where necessary.

## Validation

`turing.test.ts` verifies recognizers and rejection cases, unary output, blank input, left tape extension, deterministic shortcuts and variables, both acceptance preferences, factory selection, nondeterministic branches, traces, limits, validation.

`jff.test.ts` verifies roundtrip persistence, escaping, control points, blank tags, tape attributes, stay transitions, initial-state ordering, duplicate-transition behavior, unsupported formats, malformed files, and numeric identifier export.

`oracle.test.ts` executes the original compiled Java simulators through `docs/verification/TuringOracle.java`, using the same `Configuration.isAccept` criterion as the GUI, NORMAL-only advancement, and one-step rejected-branch visibility from `ConfigurationPane`/`ConfigurationController`. Differential checks compare acceptance, factory mode, number of steps, final tape contents, normalized head position, head-based output, halting flags, and complete state/tape/head/output snapshots at every trace node. Cases cover positive and negative 0ⁿ1ⁿ inputs, unary increment, empty input/left extension, nondeterministic branching and final-state preferences, early rejection followed by later acceptance, wildcard, negation, assignments (including Java's permissive malformed token handling), halting acceptance, literal nondeterministic wildcard behavior, and bounded loops. See `docs/verification/README.md` for reproducible commands. These tests skip when the original Java classes and oracle have not been compiled.

The original Java source and headless oracle remain available for differential verification. Test-only machines live in `desktop/tests/fixtures/machines.ts`; there is no examples catalog or graph-layout module in the application. See the verification README for commands and current coverage.
